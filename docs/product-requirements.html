Product requirements

Spawn selection

  • When the user provides a screenshot, grid reference, or named map location to illustrate a spawn-selection problem, you must treat it as an example unless the user explicitly requests location-specific behavior. Improve the general spawn-selection objective across maps; do not hard-code the pictured map, coordinate, grid cell, or nearby territories.

Tribe capture reinforcement

  • You must keep every live outbound tribe attack in the attack-candidate set, even when the tribe is temporarily absent from nearby(). Compare the live committed troops with the current Defense Post-aware capture floor on every decision pass. Reconcile and add target-specific pending intents instead of treating their mere existence as sufficient. When the combined visible and pending force is underfunded, emit only the missing reinforcement; when it already meets the floor, do not emit another attack.

Time-aware tribe clusters

  • Tribe-cluster targeting must value only the portion of a connected tribe chain that is likely to remain edible when the bot reaches it. Rival attacks and observed expansion pressure must be compounded with the number of prerequisite tribe captures. A tribe predicted to be captured before arrival must not contribute cluster value, act as a gateway to tribes behind it, occupy the bounded strategic sample, or appear in the preferred-cluster overlay.

Active attack reinforcement

  • A live outbound attack against any hostile player remains eligible for reinforcement even when its target is absent from the current nearby or border-target selector. Adequacy must include live committed troops and pending local intents, and reinforcement must emit only the missing amount up to the target-specific floor.

Defensive coverage accounting

  • When evaluating whether a candidate SAM adds protection, existing SAM coverage must be measured at each protected structure, not at the candidate SAM tile. Candidate coverage and existing coverage are separate geometric tests.

VM-backed tests

  • When a test receives objects from a node:vm sandbox, you should assert their scalar fields or normalize them before deep comparison. Objects from separate VM realms can fail strict deep equality even when their visible properties are identical.
