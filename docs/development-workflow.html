Development workflow

You always commit completed project work after its relevant verification passes. Stage and commit only the files or separable hunks owned by the current task; preserve unrelated user or agent changes in a dirty checkout. After the commit succeeds with green pre-commit checks, immediately run the project build and verify that it succeeds.

You have standing approval to create these commits without asking again. When completed task changes overlap pre-existing edits in the same task-owned files and splitting them would make the commit incomplete or incoherent, commit those affected files together instead of blocking; continue to exclude unrelated files that the task does not require.

You should run npm run lint for repository lint validation. Do not substitute a direct eslint invocation over legacy files, because the project lint script applies the ratcheted baseline that distinguishes new regressions from existing debt.

You must not use JavaScript or TypeScript catch clauses or Promise .catch() handlers in this project. They can make a broken integration look alive while silently disabling later gameplay, UI, construction, or combat phases. Let failures propagate so diagnostics and static runtime simulations fail at the original cause; use try/finally only when deterministic cleanup is required, and fix expected failure states through explicit capability checks or result values rather than exceptions.

Game constants use an exhaustive AST-backed contract. Run npm run check:constants after changing a semantic uppercase constant in engine/ or openfront-engine/src/; update the reviewed contract with node scripts/game-constants.mjs --write only when the value change is intentional. The contract is checked against the pinned upstream gitlink, alongside the existing compatibility check.

When you add a target-strength floor, preserve the explicit empty-target path: a target that reports zero or no troop count must keep the normal reserve-limited attack payload rather than being converted into a zero-troop no-op. Cover both a positive-strength floor and the empty target fallback in test/attack-intent-accounting.mjs.

Lobby bridge helpers must read configuration through the initialized lobbyState.settings object, never through an undeclared free variable. A static regression test must exercise the helper source whenever a lobby setting is forwarded to an in-game helper, because that bridge runs during startup and can otherwise prevent every UI and gameplay subsystem from initializing.

A troop donation may be reachable through both the ordinary attack-strategy list and the auxiliary policy pass. Record a successful donation at the decision tick in the shared attack behavior and reject a second donation in that same tick, even when its recipient differs. Test this directly because recipient cooldowns alone cannot prevent the duplicate path.

The donation reserve that includes friendly borders is an amount cap, not a safety verdict. Before donating, separately inspect hostile strategic Nation/Human borders: if any such army matches or exceeds ours, retain all troops. Otherwise a transfer can remove the only force preventing an immediate land invasion before a Defense Post is affordable.

OpenFront engine compatibility

The official OpenFront repository is tracked as the openfront-engine Git submodule. Every pre-commit run fetches the latest origin/main, checks out that exact revision, stages the updated gitlink, and runs the static engine compatibility test as part of the full test suite. A network failure blocks the commit so a change is never validated against a silently stale engine revision.

The updater refuses to replace local changes inside the submodule. Commit, discard, or move those changes before committing the helper. The helper's lint, formatting, and duplication tools exclude the upstream source; compatibility is enforced by test/openfront-engine-compat.mjs instead.

Game-dependent helper rules have a separate parity contract. Run npm run check:runtime-parity after changing nuke costs, blast radii or speeds, construction durations, cooldowns, unit types, or map ids. The check reads the pinned OpenFront configuration and map manifest, verifies runtime reads and reviewed fallbacks, and keeps local helper tuning (for example SAM policy ratios) outside the official game constant contract.
